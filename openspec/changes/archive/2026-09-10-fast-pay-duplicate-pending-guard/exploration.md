## Exploration: fast-pay-duplicate-pending-guard

> Source: Engram observation #6962 (`sdd/fast-pay-duplicate-pending-guard/explore`, 2026-09-09).
> Materialized verbatim; one corrupted token (`未-caught`) normalized to `un-caught`.

### Current State

`app/api/staff/students/fast-class-action/route.ts` powers staff "Fast Pay"/"Fast Sign" on the Student Payment Board.

- `resolveExistingClassPurchaseBlock` (line 87-120) is the pre-check that decides whether to block the button. It requires an `Attendance` row to already exist (`prisma.attendance.findUnique` by `userId_sessionId`), then looks up a `Purchase` matching `metadata.attendanceId == attendance.id` AND `metadata.paymentChannel` in `{cash, package_credit}`. If none found → no block, proceeds to create a NEW pending cash purchase. This misses two real cases:
  1. A pending cash purchase created by the WEB checkout flow (`app/api/checkout/cash/route.ts`) has metadata `{source:"cash_checkout", paymentChannel:"cash", settlementStatus:"pending", date, time, courseSlug}` but NO `attendanceId` (attendance is created later, at actual check-in). Since no attendance exists yet, the pre-check's own `attendance.findUnique` also returns null and the whole function short-circuits to `null` (no block) before it even reaches the purchase query.
  2. A PAID card purchase from Stripe (checkout session or payment intent) never has `metadata.paymentChannel === "cash"|"package_credit"` (its channel resolves to `"card"` via `normalizePaymentChannel` in `shared.ts`, driven by `stripePaymentIntentId`/`stripeCheckoutSessionId` presence), so the query's `paymentChannel IN {cash, package_credit}` filter excludes it entirely, even when `attendanceId` matches.
- The same narrow `(attendanceId + paymentChannel cash)` filter is duplicated in 3 places: `resolveExistingClassPurchaseBlock` (line 100-116), the inner transaction's idempotent `existingPurchase` reuse in the main `POST` handler (line 264-267), and `createPromoCash`'s inner transaction (line 176-183).
- Confirmed via the existing test `staff-fast-class-action.test.ts`: a REAL repeat Fast Pay press (same attendanceId, still-pending cash purchase) is expected to be BLOCKED (409 `pending_payment`) by `resolveExistingClassPurchaseBlock` before the transaction runs — the "silent reuse" test in the suite only exercises the transaction's belt-and-suspenders idempotency in isolation (its mocks bypass the outer prisma session/attendance lookup). So **block-on-existing-purchase, not silent reuse**, is the established pattern this codebase already uses for the cash+attendanceId case; the fix widens the SAME pattern rather than introducing new behavior.
- `PURCHASE_STATUS` (`lib/payment-constants.ts`) has no cancel/void/refunded-aware branch in the block logic — today, ANY non-`"paid"` status (including a hypothetical `"refunded"`/`"failed"`) falls into the `pending_payment` block branch. This is a latent related bug: a refunded/failed purchase for the same attendanceId would permanently block Fast Pay. Worth excluding `status IN (failed, refunded)` from the match when widening.
- Board side: `dedupEnrichedPurchasesBySlot` (`payments-loader-purchase.ts`) collapses same-slot purchases for DISPLAY using `buildPurchaseAttendanceDedupKey` → `attendanceSlotKey(userId, courseSlug, classStartsAt.getTime())` (falls back to `purchase:{id}` when courseSlug/classStartsAt missing). `classStartsAt` is derived from `metadata.date`+`metadata.time` via `buildSessionStartsAt`, or `purchase.createdAt` as fallback. This dedup only affects what the board RENDERS.
- Outstanding balance is computed separately and is NOT deduplicated: `buildOutstandingBalanceByUser(globalPurchases)` in `payments-loader.ts:198` and `buildOutstandingBalanceByUser(purchases)` in `app/api/staff/students/search/route.ts:524` both sum over RAW (non-deduped) purchases via `isOpenPurchase` (`shared.ts:166-179`). `isOpenPurchase` treats a purchase as "open" whenever `settlementStatus !== "paid"` AND (`!isCompletedPaymentStatus(status)` OR `paymentChannel === "cash"`) — i.e. a cash purchase counts as open regardless of its `status` field, only `settlementStatus` (a metadata field staff toggles) closes it. This is why a hidden duplicate still inflates "Outstanding balance" even though the board only shows one row for the slot.
- `metadata.date`/`metadata.time` is a consistently-set slot key across ALL purchase-creation paths examined: fast-class-action's own cash purchase (line 269), `createPromoCash` (line 193), and web `checkout/cash` (lines 188-189, 241-242). This confirms `(userId, courseSlug, metadata.date, metadata.time)` is a safe, already-established slot identity independent of `attendanceId`.
- UI: `components/front/staff/FastClassActionControls.tsx` already generically surfaces ANY non-2xx `error` message from the endpoint in a blocking modal (lines 29-33, 110-131). No UI change is needed for a creation-side fix — existing `pending_payment`/`completed_purchase` codes and messages are generic enough to cover the card/web cases too.
- Existing test coverage lives in `tests/api/staff-fast-class-action.test.ts` (Prisma fully mocked via `vi.mock("@/lib/prisma")`, `mockTx` for transaction calls). Test command: `npm test` (`vitest run`, per `package.json` and `openspec/config.yaml`).

### Affected Areas

- `app/api/staff/students/fast-class-action/route.ts` — `resolveExistingClassPurchaseBlock`, the main `POST` handler's inner `existingPurchase` reuse query, and `createPromoCash`'s inner `existingPurchase` reuse query all need the widened slot-match. Candidate for one small extracted helper (Rule of Three — exact same OR/AND shape needed 3 times).
- `tests/api/staff-fast-class-action.test.ts` — needs new/modified cases: web-style pending cash purchase (no attendanceId, date/time match) blocks Fast Pay; paid card purchase (Stripe evidence, no paymentChannel cash/package_credit) blocks Fast Pay; refunded/failed purchase does NOT block; promo path (`createPromoCash`) gets equivalent duplicate coverage.
- `app/api/staff/payments/shared.ts` — read-only reference for `isCompletedPaymentStatus`/`normalizePaymentChannel`/`isOpenPurchase`, reusable instead of re-deriving a 4th "is this paid" definition inside fast-class-action.
- Not required for PR1, optional follow-up: `app/api/staff/payments/payments-loader.ts:198` and `app/api/staff/students/search/route.ts:524` (`buildOutstandingBalanceByUser` callers) — board-side defense so any pre-existing/un-caught duplicate doesn't inflate outstanding balance while hidden by `dedupEnrichedPurchasesBySlot`.

### Approaches

1. **Creation-side guard only (widen the existing block/reuse pattern in fast-class-action route.ts)** — extend the WHERE clause in all 3 call sites to match by `(userId, courseSlug, date, time)` OR `attendanceId`, any paymentChannel, excluding `failed`/`refunded` status; classify paid-vs-pending using the shared `isCompletedPaymentStatus` helper.
   - Pros: Fixes the actual root cause (bug is at creation, not display); reuses the exact 409/message/UI pattern already shipped and tested; smallest diff; matches "the correct fix usually deletes or relaxes something" (this relaxes/widens a query, adds no new state/verb/flag).
   - Cons: Does not retroactively protect against a duplicate created by some OTHER, unaudited creation path (only the audited ones — fast-class-action's own paths — are covered).
   - Effort: Low.

2. **Creation-side guard + board-side outstanding-balance dedup (bundle PR1+PR2)** — also make `buildOutstandingBalanceByUser` sum over slot-deduplicated purchases (same key as `dedupEnrichedPurchasesBySlot`).
   - Pros: Defense in depth; also fixes the display of ANY pre-existing prod duplicates (Richmond/Christian's already-created rows) without a manual DB cleanup.
   - Cons: Touches a function shared by 2 unrelated callers (board loader + profile search) — a second root-class change that should get its own single fix per the systemic-issue-triage skill ("2+ issues share a root = ONE fix at the root"), not bundled ad hoc into the creation-side PR; risks exceeding the 400-line review budget in one PR; changes historical/global balance semantics that deserves its own review.
   - Effort: Medium.

3. **Reuse-and-attach instead of block** (on finding an existing pending cash purchase without attendanceId, attach `attendanceId` to it instead of blocking) — rejected as primary approach: it's new "attach" transaction machinery (violates the over-engineering test), diverges from the codebase's own established "block on existing pending" precedent for the attendanceId+cash case, and risks a race with a customer's in-flight self-checkout completing on the same purchase row.

### Recommendation

Approach 1 for PR1 (creation-side guard only). It is a strict widening of an already-tested, already-shipped pattern (same codes, same messages, same UI, same "reuse inside the transaction as belt-and-suspenders" shape) — no new states, verbs, or UI surface, and it closes both reported production incidents at the actual creation site. Extract one small helper for the repeated slot-match WHERE clause (used 3x) rather than tripling the literal Prisma filter. Reuse `isCompletedPaymentStatus` from `shared.ts` for the paid/pending classification instead of a 4th bespoke definition.

Treat Approach 2 (board-side outstanding-balance dedup) as an explicit, separate, optional follow-up change — do not bundle it into this PR. It shares a root with a second call site (`search/route.ts`) and deserves its own single fix + review rather than being folded into the fast-pay bugfix.

### Risks

- Prod already has 2 confirmed duplicate rows (Richmond, Christian) predating this fix; those will keep inflating "Outstanding balance" until either manually settled by staff via the existing mark-paid action or a separate data-cleanup task (not code) is run — this exploration did not touch the DB per instructions, so exact scope of existing duplicates is unconfirmed beyond the 2 named incidents.
- Widening the match to "any paymentChannel" for the block could theoretically block a legitimate NEW purchase if a courseSlug+date+time collision happens across genuinely different sessions (e.g. schedule reused across weeks) — mitigated because `metadata.date` is a specific calendar date, not a recurring weekday, so this should not occur in practice; worth a scenario in spec.md regardless.
- `attendanceSlotKey`/`buildPurchaseAttendanceDedupKey` in the board is marked `@deprecated ... use attendanceSlotKeyByDatetime`, yet `buildPurchaseAttendanceDedupKey` still calls the deprecated ms-based `attendanceSlotKey` — inconsistent naming/deprecation but functionally equivalent (both ultimately keyed off date+time). Out of scope to "fix" the naming here; noted so sdd-design doesn't assume `attendanceSlotKeyByDatetime` is actually wired in.
- Estimated diff size: ~80-150 production lines (3 call sites widened + 1 extracted helper) + ~150-250 test lines (4-6 new/modified cases across both the main handler and `createPromoCash`) ≈ 250-400 total changed lines — near the 400-line PR budget. Recommend keeping PR1 strictly to the route.ts guard + its direct tests; do not add the board-side change even as a "small addendum."

### Ready for Proposal

Yes. Root cause is confirmed by direct code reading (not just the incident report's hypothesis), the fix pattern is already established elsewhere in the same file, and scope for PR1 is unambiguous: `app/api/staff/students/fast-class-action/route.ts` + `tests/api/staff-fast-class-action.test.ts` only. Tell the user: recommend `sdd-propose` next, explicitly deferring the board-side outstanding-balance dedup to its own later change.
